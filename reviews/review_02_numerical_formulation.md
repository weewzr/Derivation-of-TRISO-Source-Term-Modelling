For the intended five-layer production problem, this requires:

1. histories born uniformly in the kernel;
2. each history propagated through the five-layer WOS process;
3. an actual release time (	au_m) recorded for each history;
4. release counted only when (	au_mle t).

### What the supervisor repository actually provides

The dedicated:

That routine continues taking complete WOS hops until:

[

]

It does not stop a hop at the exact requested time.

Therefore a history can cross the absorbing outer surface during a hop whose endpoint occurs after the requested observation time, and the live ensemble can mark it released even though the actual simulated release time is greater than the requested (t).

This makes the fixed-time observable

[

=
rac1Nsum 1[	au_mle t]

**different from the current live-ensemble observable** whenever a WOS hop overshoots the observation time.

This is not merely a missing convenience wrapper.

It means the claimed Review-2 mathematical observable:

[

]

does not yet have a one-to-one production implementation for the intended five-layer benchmark.

At present there are three different things:

1. **bare-kernel release-time ensemble** — implemented;
2. **five-layer individual release-time walk** — implemented;
3. **five-layer fixed-time release fraction** — not implemented as the documented estimator.

### Consequence

The production numerical contract cannot yet be said to accurately reconstruct the supervisor implementation for the primary observable.

A detailed implementation verification cannot reliably compare a five-layer WOS release curve to a continuum reference until the actual five-layer release-time ensemble semantics are fixed.

### Required remediation

Do not change the WOS interface rule.

[

Keep the current frame-animation path separate from the release-time verification path if appropriate.

# 15. Max-step censoring

**R2-M03 — MAJOR**

**Location:** `walk_on_spheres.rs::walk_until_released`; `ensemble.rs::released_fraction`; `docs/triso/21_frozen_production_wos_contract.md`.

The individual multilayer release function returns:

[
None
]

when `max_steps` is reached before release.

The generic `released_fraction(outcomes)` helper, however, computes:

[
rac{#{	ext{Released outcomes}}}
{#{	ext{all outcomes}}}.
]

Thus censored histories are included in the denominator as if they represented known non-release at the observation endpoint.

For a finite step budget this is not ordinary Monte-Carlo sampling uncertainty.

It is censoring/truncation.

### Consequence

If such a helper were used as a release estimator, it would produce a downward-biased release fraction whenever non-negligible histories hit the step cap.

### Required remediation

The numerical contract must explicitly distinguish:

- released;
- still alive at the requested time;
- censored by maximum steps;
- abnormal/invalid histories.

The fixed-time estimator must state how censored histories are handled.

Do not silently fold them into the unreleased population unless the resulting estimator is explicitly defined as a lower-bound/censored estimator.

### Evidence required for closure

A concrete estimator equation and code path showing how max-step histories are classified.

Review 3 — implementation, with consequences carried into Review 4 verification.
